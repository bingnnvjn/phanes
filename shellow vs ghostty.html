Shellow vs Ghostty

Fable（寓言）渲染器研究对比报告 —— 以 Ghostty 官方渲染器为"天花板"，看安卓端最接近的实现 Shellow 做到了哪一步
调研日期：2026-08-07 ｜ 范围：libghostty-vt 核心不变，只对比"渲染状态 → 画法层" ｜ 全部信息经一手来源核实
一句话结论：Ghostty 官方渲染器定义了"高性能终端渲染"的完整架构；Shellow 是安卓上最接近这套架构的现成开源实现（Rust + wgpu + Vulkan）， 已经实现了约 60% 的核心技术（字形图集、一次 draw call、文本整形、脏行跟踪、选择/搜索叠加）， 剩下 40% 是简化版或占位（正文不走官方迭代器、图集整张重传、没有彩色 emoji、符号自绘是占位）。 Fable 的路线 = 以 Shellow 为骨架，按官方思路补齐这 40%。

Plain Language 白话版：三个结论

白话 第一，显卡画字是必须的，官方用的是一套"高性能三件套"。

手机 CPU 一个个画字会卡。官方的方法是：先把用到的字"烤"成一张纹理图集（像把菜谱提前做成预制菜）， 然后一条命令把一屏的字一起画出去（批量），最后只重画有变化的那几行（不整屏重来）。这三件事，就是终端渲染性能的核心。

白话 第二，Shellow 是安卓上把这套三件套做得最全的现成代码。

它是 GitHub 上一个开源手机终端 + Codex 客户端（Apache-2.0，安卓 Google Play 测试版、iOS TestFlight 都在跑）。 它的架构和我们 Fable 几乎一模一样：Kotlin/Compose 壳 + Rust 内核 + ghostty 核心 + wgpu 渲染。等于有人替我们先把最难的路趟了一遍。

白话 第三，但它"偷懒"了几处，我们要补。

它读正文是一个格子一个格子地要数据（慢）；字形图集一有新增就整张重新上传（浪费）；没有彩色 emoji 通道； 画边框线这类符号用的是临时噪点占位（不好看）。这些正好是官方架构里已经给出答案的部分 —— 我们照着官方补齐即可。

Mental Model 先建立坐标系：终端渲染的三层

①核心（引擎）＝ libghostty-vt
负责解析终端字节流、维护屏幕格子、滚动缓冲。它不认识屏幕，只维护"数据"。Fable 已定：这层不变。
②渲染状态 ＝ 核心交给画家的"数据包"
脏标记（哪几行变了）、每格文字/颜色/样式、配色板、光标位置。官方用 C API（ghostty_render_state_*），Rust 侧有安全封装。
③画法层 ＝ 怎么把数据变成像素（本文主角）
字形图集、GPU 绘制、shader、脏行上传。官方渲染器和 Shellow 渲染器都在这层，只是实现深度不同。

本次对比只发生在第 ③ 层：同一个核心、同一份渲染状态数据，两家"画法层"分别做到了什么程度。

Ghostty Official 官方渲染器架构解剖（2026-05 大重构后）

官方渲染器在 2026 年 5 月做了一次大重构：把原来分开的 Metal / OpenGL 两套逻辑，统一成"一个通用渲染器 + 图形 API 抽象层"。整体拆成三大块：

① 渲染线程模型

  • 每个终端窗口一个独立渲染线程，和 UI 线程、I/O 线程分开
  • 通过 mailbox 收消息（焦点、尺寸、配置、搜索结果……）
  • 定时器：120 FPS 刷新、600ms 光标闪烁
  • demand lock：渲染线程要锁时"喊一声"，I/O 线程让路，防止高频输出饿死渲染
  • 取帧 = RenderState.beginUpdate → 快照 → endUpdate，锁只占一瞬间
白话：后台有个专职画师，和前台互不干扰；前台数据多的时候画师还能插队。

② 通用渲染器（怎么画）

  • 多通道（multi-pass）：背景、文字、图片、全屏后期各一个专用 shader
  • 实例化绘制：把所有字形拼成一个数组，一次 draw call 画几千个字
  • 每个字形实例 32 字节：图集位置、大小、bearing、格子坐标、颜色、用哪个图集
  • Uniform 携带全局状态：格子尺寸、网格行列数、光标位置/颜色、背景色、对比度等
  • 颜色管理：sRGB / 线性混合、WCAG 最低对比度
白话：一次"批量打印"整屏字，而不是一个字一个字打印。

③ 字形管线（字从哪来）

  • 字形图集：字形光栅化成位图，塞进 GPU 纹理（方形 bin-packing）；灰度 + 彩色两张图集
  • 图集变化通过原子计数器通知 GPU 增量同步
  • sprite face：边框线、下划线、光标、盲文这些符号自己用 2D 画，不依赖字体
  • 三套光栅后端：FreeType / CoreText / 自研 OpenType glyf 轮廓光栅器
  • 两级缓存（SharedGrid，读写锁）：命中走读锁，未命中才渲染新字形；跨窗口共享
  • Nerd Font 约束：数千个码点带对齐规则，图标不乱
白话：常用字提前烤好放在纹理里反复用；连"画线画框"都有专门的"绘画程序"。

Three Gaps 三个最值得注意的差距（深度解释）

① 正文读取走了"慢路径"。官方设计是让渲染器通过 RenderState 的行/格迭代器一次拿整块数据； Shellow 却逐格调用 grid_ref().graphemes()，每帧 O(列×行) 次 FFI 调用。 对 80×30 的小屏压力不大，但对"多会话并行、输出量大"是隐患。我们做的时候直接用 RowIterator / CellIterator（betamax 已示范正确用法）。
② "脏行"只做了一半。脏行从 RenderState 算出来了，也上传了，但绘制时还是重建全部顶点。 真正的优化应该是"只有脏行的顶点重新上传"。这是我们可以直接做对的地方。
③ 没有彩色 emoji 通道，也没有规范的自绘符号。fontdue 只能光栅化灰度字形，emoji 会落到噪点占位。 对跑 AI Agent 的场景，输出里常带 emoji 和特殊符号 —— 这两块要用官方架构的答案补：彩色图集 + sprite face。

Fable Blueprint 由此得出的 Fable 渲染器模块清单

模块 1

快照层（核心 → 渲染器的数据）

借：Shellow 的 ghostty_adapter 思路 + 快照结构（脏行/行文本/样式 run/光标/模式/滚动）
改：正文改用 RenderState 迭代器，脏行从 RenderState 的 Dirty::Partial + 每行 dirty 取
模块 2

字形管线（字体 → 纹理）

借：Shellow 的字体路径列表、rustybuzz 整形、fontdue 光栅
补：灰度 + 彩色双图集、增量上传、sprite face 自绘符号（按官方架构）
模块 3

顶点构建（数据 → 顶点）

借：Shellow 的 SurfaceFrameBuilder（文本 quad + 背景矩形 + 下划线 + 光标 + overlay）
改：按脏行增量重建顶点，而不是每帧全量
模块 4

GPU 层（wgpu）

借：Shellow 整段 —— SurfaceView/ANativeWindow 接入、单 draw call、WGSL shader 骨架
补：按需升级多通道（背景/文字/图片/后期分开）
模块 5

渲染驱动 + 壳（Kotlin）

借：Shellow 的 SurfaceView + 内容签名触发渲染模式
改：滚动条、输入法、多会话 Tab 等壳层按 Fable 需求自建
模块 6

构建管线（libghostty-vt 安卓编译）

参考：Shellow 的 libghostty-vt-sys（安卓构建补丁 + 生成绑定）
现状：先用 expo 预编译库（工单 08 已验证），后置迁移
最终结论：Shellow 给了我们 60% 的完整骨架（GPU 路径、shaping、图集、overlay、安卓接入全部跑通）， 剩下 40% 是往官方架构补齐 —— RenderState 迭代器取正文、双图集 + 增量上传、sprite face、真脏行增量。 "以 Shellow 为骨架、向官方架构补全" 的路线，至此有了第一份具体的模块清单。
