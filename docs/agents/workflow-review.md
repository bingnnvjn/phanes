# Fable 工程工作流审查与改进建议

> 审查日期：2026-08-12  
> 审查对象：`docs/agents/workflow.md` 及其直接引用的 SSOT、工单和启动包  
> 本文件是审查报告，不是新的流程 SSOT。流程规则仍以 `docs/agents/workflow.md` 为准。

## 背景

Fable 的工程流程负责把一个方向变成可实施工单，再让新 Agent 在干净上下文中完成一张工单。

当前主流程是：

1. 决策阶段：确定方向，更新规格和 ADR。
2. 拆单阶段：创建垂直切片工单及启动包。
3. 实施阶段：按工单验收清单修改 Kotlin 壳、Rust 底层、核心或相关工程资产。
4. 收尾阶段：评审、验证、提交，并把结论写回工单 Comments。
5. 下一步推荐：读取路线图和工单依赖，找出可以开工的 frontier。

这套主流程可以继续使用，不需要重做。

## 当前问题

主要问题是工程资料有重复内容。重复内容会随时间产生不同步。

例如：

- `workflow.md`、`项目总览与交接.md` 和工单文件都记录了方向状态。
- 工单 23 是 `待验收`，但依赖它的工单 27 已经是 `已完成`。
- 部分项目总览内容仍显示旧进度。
- 仓库有 40 张工单和 39 个启动包；工单 16 没有启动包。工单 16 是 backlog，但当前规则没有说明这是允许的例外。
- `issue-tracker.md` 要求使用纯文本 `Status:`，但它的格式示例使用了加粗的 `**Status:**`。
- 部分已完成工单仍有未勾选的验收项。
- 部分旧工单的 `Blocked by` 没有使用完整的 `fable-v1/NN` 格式。

这些问题不影响 Kotlin 壳、Rust 底层、会话层、渲染器或 CoreAdapter 的运行。它们影响 Agent 对项目状态的判断。

风险是：新 Agent 可能读到旧状态，选择错误的 frontier，或错误地判断一张工单已经完成。

## 建议一：让 workflow 成为唯一入口

`workflow.md` 应是唯一入口，不应称为唯一依赖。

建议使用以下定义：

> `docs/agents/workflow.md` 是工程任务的唯一入口。它负责判断任务类型，并指向对应的 SSOT、工单和启动包。

Agent 从 `workflow.md` 启动，但仍需读取：

- 工单本体：任务、状态、依赖和验收。
- 启动包：本工单的环境快照、路径和红线。
- `CONTEXT.md`：Fable 领域词汇。
- ADR：Kotlin 壳、Rust 底层、核心、CoreAdapter 等已定决策。
- `项目总览与交接.md`：项目速览、工具链和红线。

完成条件：`workflow.md` 不再声称其他文件不是启动依赖，且启动协议明确列出必须读取的事实源。

## 建议二：从 workflow 删除动态状态

`workflow.md` 可以保存稳定的方向映射：

- 方向名称。
- 对应 ADR。
- 对应规格决策。
- 对应工单集合。

`workflow.md` 不应复制：

- 工单当前状态。
- 当前 frontier。
- 已完成日期。
- 下一张工单。

这些动态事实应来自工单文件。项目总览可以展示路线，但它是视图，不应覆盖工单状态。

完成条件：修改一张工单的 `Status` 后，不需要同时修改 `workflow.md`。

## 建议三：增加工单一致性检查器

建议新增一个只读脚本，例如：

```text
scripts/check-issues.sh
```

检查器应验证：

1. 每张实施工单都有启动包；backlog 工单可以用显式字段豁免。
2. 每张工单有且只有一个纯文本 `Status:`。
3. `Status` 使用 `issue-tracker.md` 定义的词汇。
4. `Blocked by` 使用 `fable-v1/NN` 或 `None`。
5. 每个依赖工单都存在。
6. 依赖图没有环。
7. 已完成工单的前置依赖已经完成，或有明确豁免记录。
8. 已完成工单的验收项全部勾选，或每个未完成项都有 `Waived` 原因。
9. Comments 包含验证数据、坑与解法、结论写回。
10. 输出当前 frontier：`待开工` 且全部依赖已完成的工单。

检查器只读取资料，不修改工单。

完成条件：一条命令可以报告全部格式错误、状态冲突和当前 frontier；退出码可以供 Agent 或 CI 判断 PASS/FAIL。

## 建议四：明确工单完成语义

建议统一以下规则：

- `待开工`：依赖允许开工，但实施尚未开始。
- `进行中`：Agent 正在实施。
- `待验收`：程序化验证已完成，但仍需用户或真机确认。
- `已完成`：全部验收项已完成，或未完成项已有明确豁免。
- `挂起（原因）`：当前不能继续，并记录具体原因。

如果用户决定跳过一个验收项，Comments 应记录：

```text
Waived by: 用户决定，2026-08-12
Reason: ...
Impact: ...
```

下游工单通常只依赖 `已完成` 工单。如果下游只需要上游的某个程序化产物，应在 `Blocked by` 附近明确说明该依赖条件。

完成条件：Status、验收清单、Comments 和依赖图表达同一个事实。

## 建议五：把启动包作为可刷新缓存

启动包应只保存本工单的增量：

- 工单特有决策。
- 工单特有路径。
- 工单特有红线。
- 上游工单对本单的结论。
- 环境事实的核实日期和 SSOT 指针。

通用工具链版本、通用构建命令和全局架构决策不应复制到每个启动包。Agent 开工时从 SSOT 读取并核实这些事实。

完成条件：工具链变化时，只需修改权威文件；旧启动包不会继续声明过期版本。

## 建议六：让流程语义不依赖特定技能

`workflow.md` 中的 `/to-spec`、`/to-tickets`、`/implement` 等名称可以保留，但每个阶段应同时定义：

- 输入。
- 必须执行的动作。
- 产出。
- 完成条件。

如果当前 Agent 有对应技能，可以使用技能。如果没有技能，Agent仍可以按阶段契约完成任务。

完成条件：更换 Agent 环境后，工程主流程仍可以执行。

## 建议七：提交前保护已有改动

实施会话开始时记录：

- 涉及的 Git 仓库。
- 初始 `git status --short`。
- 用户已有改动。
- 本工单允许修改和提交的文件。

提交前再次检查 diff，只暂存本工单文件。

完成条件：工单提交不包含用户原有改动或其他工单的文件。

## 推荐实施顺序

先完成以下三项：

1. 明确 `workflow.md` 是唯一入口，并移除动态状态副本。
2. 增加工单一致性检查器。
3. 统一完成状态、验收豁免和依赖语义。

然后再处理：

4. 精简启动包中的重复环境信息。
5. 为没有对应技能的 Agent 补充阶段契约。
6. 增加脏工作树和提交范围检查。

## 预期结果

完成这些改进后：

- 工单文件继续作为状态、验收和进展的 SSOT。
- ADR 继续保存 Kotlin 壳、Rust 底层、核心、会话层和 CoreAdapter 的架构决策。
- `workflow.md` 只负责引导 Agent 到正确事实源。
- Agent 可以用一条命令得到可信的 frontier。
- 新会话不会因为旧路线状态或旧启动包而选择错误工作。

最终目标不是增加更多流程文件，而是让每个事实只有一个权威位置，并让自动检查及时发现资料漂移。
