# Issue tracker：本地 Markdown

本仓库的 issue 与规格（spec）以 markdown 文件存放在 `.scratch/`。本文件是工单体系的规则权威（SSOT 见 `docs/agents/ssot.md`）。

## 目录结构

- 一个功能一个目录：`.scratch/<功能名>/`（当前唯一：`fable-v1`）
- 规格文件：`.scratch/<功能名>/spec.md`
- 实施 issue：每张工单一个文件 `.scratch/<功能名>/issues/<NN>-<标题>.md`，从 `01` 编号——绝不合并
- 实施提示词（启动包）：`.scratch/<功能名>/实施提示词-工单<NN>.md` —— 只放**增量**（会话设置/环境快照/已定决策/红线/收尾），**任务本体单一来源 = 工单文件**，不复制验收清单

## 工单状态词汇（唯一）

每张工单顶部必须有 `Status: <词>`（**纯文本行，便于 grep；不加粗、不用 `**`**）。

| 状态 | 含义 |
| --- | --- |
| 待开工 | 已建单、未开始 |
| 进行中 | 正在实施 |
| 待验收 | 实施完成，等验收（真机/用户确认） |
| 已完成 | 验收通过，结论写回 |
| 挂起（原因） | 被阻塞 / 待人工 / backlog，括号写明原因 |

历史标签映射：`待Agent处理` → `待开工`；`待人工处理` → `挂起（待人工）`；`待分类` → `挂起（待分类）`。已按此映射统一（2026-08-07）。

## 工单文件结构

```markdown
# NN — 标题
**What to build:** 目标与边界
**Blocked by:** fable-v1/NN 或 None
**Status:** 待开工

## 验收清单
- [ ] ...

## Comments
（每轮进展追加；完成标准见下）
```

- 工单号引用写全名：`fable-v1/09`（未来多功能目录不撞号）
- `Blocked by` 写全名或 `None`
- **工单只描述行为，不写具体文件路径**（路径易过期）；实现所需路径统一放实施提示词的"环境快照"（to-tickets 约定）
- 工单是垂直切片：每片窄但完整、可独立验证、大小适配一个干净上下文（to-tickets 约定）

## 完成标准（每张工单收尾必写）

Comments 至少追加三样，缺一不算完成：

1. 验证数据/命令（关键输出、构建结果、真机现象）
2. 踩过的坑与解法
3. 结论写回（对后续工单/决策的影响）

## Triage 标签（仅外部来单/backlog）

`docs/agents/triage-labels.md` 的五角色标签只用于"外部来单需要分类"；**工单运行状态一律用本文件的状态词汇**，两套不混用。

## 信息新鲜度规则

- 所有"现状/版本/工具链/资产"类信息必须带**核实日期**（如 `（2026-08-07 核实）`）
- 动手前若任务涉及外部事实（库版本、支持情况），先做新鲜度检查，不拿旧消息开发

## 进展惯例

- 开跑前把 `Status` 改为 `进行中`
- 每轮进展追加到 `## Comments`（带日期）
- 完成时按"完成标准"写收尾记录，改 `Status: 已完成`（需真机确认则先 `待验收`）
