# 44 — 会话输出批处理与回调收尾

**What to build:** 把 Rust 会话输出从“每个 4KB chunk 一个主线程任务”改为有界批处理；统一事件 dispatcher、Java 主线程 drain、callback generation 和 close 顺序，保证高输出流畅且关闭后不再投递旧事件。

**Blocked by:** fable-v1/43
Status: 待验收

## 验收清单

- [ ] 每会话输出使用有界队列并合并连续 chunk，主线程同一时刻最多一个 drain runnable
- [ ] 队列背压策略明确且输出完整性测试通过
- [ ] close 后旧 generation callback 不再触达已关闭会话或 Activity
- [ ] 日志 dispatcher 可停止或有明确进程级所有权，不永久占用失效 callback
- [ ] 4 会话 180 万行场景输出完整、无 ANR，主线程队列和分配数据可对比

2. 踩过的坑与解法：
   - 仅把 Rust 每个 4KiB read 合并不足以防 UI 饥饿；JNI 先按 64KiB/4ms 合批，Java 再设 1MiB 有界输出队列、256KiB 单次 drain 预算，满队列阻塞 native producer 而不丢字节。
   - 已出队事件若在 consumer 调用前 close 会越过 generation；Java drain 与 `close()` 在同一锁内串行，Rust `EVENT_CALLBACKS` 锁也与 callback 撤销串行，close 返回后旧 callback 不会触达会话或 Activity。
   - `jniLibs` 的 `.so` 被忽略，单改 Rust 源不会进入 APK；新增 Gradle `preBuild` 依赖，以锁定的 arm64 Android target 从已跟踪 Rust 源重建并复制产物。
3. 结论写回：
   - 会话输出链现为 Rust reader 4KiB → JNI 64KiB/4ms 批次 → Java 1MiB 有界队列 → 每轮最多 256KiB 的单主线程 drain；输出完整性选择背压而非丢弃。
   - 日志 dispatcher 明确为进程级、随 `libfable-session` 生命周期存在；`sessionSetLogCallback(null)` 释放旧 Java 全局引用，不永久持有失效 callback。
   - 工单 45/46 可假定 close 后 native 旧 generation 不会再进入 Kotlin/Java；仍须先完成本单真机 baseline 复验后才把“无 ANR/分配对比”结论用于后续性能判断。
