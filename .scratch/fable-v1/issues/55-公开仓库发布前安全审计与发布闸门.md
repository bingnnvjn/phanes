# 55 — 公开仓库发布前安全审计与发布闸门

**What to build:** 在 Fable 任何源码或 Rust crate 推送到公开 GitHub 仓库前，完成发布边界、Git 历史、签名材料、隐私、许可证、供应链、GitHub Actions、分支保护和泄露响应的安全审计，并建立可重复的公开发布闸门。
**Blocked by:** fable-v1/60、fable-v1/61、fable-v1/59、fable-v1/51
Status: 挂起（等待工单60、61、59、51）

## 验收清单

- [ ] 明确公开仓库拓扑：`fable-boo`、`spike-render`、`spike-session` 的远端、目录边界和历史保留策略
- [ ] 根仓库内部规划、诊断、设备记录和实施资料不会误入公开源码仓库
- [ ] 应用签名测试材料已完成用途/私钥可用性分类；真实签名材料不在公开发布范围；必要时完成历史清理和密钥轮换
- [ ] 工作树、索引、全部 branch/tag 和 Git 对象通过专门 secret scanner
- [ ] 第三方源码、vendor、字体、libghostty、Termux 来源和许可证清单完整
- [ ] 每个公开 Rust crate 有顶层许可证、README、`SECURITY.md`、`CODEOWNERS` 和公开贡献规则
- [ ] 公开 CI 使用 `pull_request`、最小权限、无 PR 发布 secret、GitHub-hosted runner 和固定 Action SHA
- [ ] fmt、严格 Clippy、全目标测试、rustdoc、`--locked`、`cargo deny` 和供应链台账均可程序化验证
- [ ] 分支保护将这些 job 设为 required checks，并要求独立 Agent 审查；管理员绕过被禁止或可审计
- [ ] 故意失败 PR 证明 required check 会阻断合并；公开后匿名检查、artifact 和日志不含敏感内容
- [ ] 已在临时 private 仓库完成一次完整预演，再从同一份已审计 refs 创建 public 仓库
- [ ] 建立凭据撤销、历史清理、公告和责任人流程

2026-08-15 实施与闸门验证：

1. 验证数据/命令：
   - 新增 `scripts/public-release-gate.sh` 和
     `docs/security/public-release-gate.md`。闸门只读、fail-closed，检查三个
     独立 crate 的公开路径 allow-list、远端冻结、敏感文件、工作树、索引、
     refs/reflog、可达/不可达 Git 对象和发布前工具依赖；不创建远端、不推送、
     不改写历史、不启用 workflow。
   - 拓扑复核发现 `fable-boo` 没有自己的 `.git`，`git -C fable-boo
     rev-parse --show-toplevel` 返回 Fable 根仓库；它当前不是独立 Git 仓库。
     闸门已收紧为“crate Git 顶层必须等于 crate 目录”，因此该项明确失败。
   - `scripts/public-release-gate.sh`（2026-08-15，最终拓扑检查）结果：
     `51 checks, 11 failures`。初始运行曾报告 `61 checks, 11 failures`；收紧
     `fable-boo` 独立仓库检查后，它直接作为拓扑阻断项失败，不再继续伪装成独立
     crate 的后续检查。内建 marker 扫描对根仓库、三个 Rust crate 和 `fable-app`
     的工作树及 Git 对象均未发现已知 token/private-key 标记；专用 gitleaks 未安装，
     故闸门保持失败。
   - `scripts/rust-quality-gate.sh` 及公开闸门内置调用：`15 steps, 0 failed`。
     三个 crate 的 fmt、check、严格 Clippy、全目标测试、rustdoc 均通过；FreeType C 编译仍有
     已知 `unused variable: memory` 警告，但不影响 Rust 门禁结果。
   - `scripts/rust-supply-chain-gate.sh`：因环境缺少固定版本
     `cargo-deny 0.20.2` 退出，供应链预演不能宣称完成。
   - `cargo metadata --locked --no-deps` 三个 crate 均通过；`git diff --check`
     根仓库及三个 crate 均通过。
   - `keytool -list -v` 将 `fable-app/app/<上游测试签名材料>` 分类为
     `PrivateKeyEntry`。未读取或输出任何密码/私钥；私钥密码可用性仍未验证，
     因此按“潜在可用签名材料”处理，公开 `fable-app` 前必须轮换并从所有公开
     refs 排除。

2. 踩过的坑与解法：
   - 目标发布形态是三个独立 Git 仓库，但当前 `fable-boo` 仍在根仓库工作树；
     根仓库的发布清单不能用 `git add .` 代替。闸门将三个 crate 的允许路径分开，
     并把 `target/`、`out.png`、coverage、日志、
     keystore、APK/AAB 和环境文件作为阻断项。
   - 工作树含 Android/Gradle 生成目录，内建文本扫描会把二进制产物当噪声；
     扫描器跳过明确的生成缓存目录，但专用 gitleaks 仍必须在发布前扫描完整输入。
   - `PrivateKeyEntry` 只证明 keystore 条目类型，不证明未知 key password；
     闸门文案已改为“潜在可用、密码可用性未验证”，避免过度结论。
   - 工单 51 的红线禁止在 Fable 自有远端确认前新增 Rust workflow；因此 CI、
     required checks、分支保护和故意失败 PR 仍保留为发布前人工闸门。

3. 结论写回：
   - 已完成可重复的本地公开发布闸门，以及三个 crate 的 README、LICENSE、
     SECURITY、CONTRIBUTING、CODEOWNERS 和第三方来源基线；`spike-render`、
     `spike-session` 的 Cargo manifest 也声明 MIT。
   - 工单不能标记“已完成”或“可公开”。当前阻断项为：`fable-boo` 尚未拆为独立
     Git 仓库；`<上游测试签名材料>` 轮换/历史排除与人工用途确认、专用 secret
     scanner、`cargo-deny`、
     Fable 自有远端、CI workflow/required checks、分支保护、private 预演、
     匿名检查、JetBrains Mono 字体来源与许可证证据、以及安全响应责任人。
   - 后续恢复条件：先由人工提供并确认 Fable 自有远端及管理员权限，安装并固定
     审计工具，完成签名材料轮换/历史策略和第三方资产清单；然后按工单 51 接 CI
     与分支保护，完成 private rehearsal 和故意失败 PR，最后才允许创建 public
