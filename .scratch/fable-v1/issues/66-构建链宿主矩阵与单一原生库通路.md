# 66 — 构建链宿主矩阵与单一原生库通路

**What to build:** 把"APK 里那四个原生库从哪里来"固定成一条明确、可复现的通路。现在这条路依赖设备上手工造的假 NDK：AGP 9 下产物进不了 APK，第二个设备（x86_64 电脑）的步骤在仓库里也没有记录。本单交付四样东西：宿主支持矩阵（写进文档）、一个仓库内的原生库生成脚本、真实的产物 ABI 范围、能拦住缺库的构建校验。修完，工单 65 的验证与推送才有前置条件。

**Blocked by:** None
Status: 待开工

## 验收清单

- [ ] 宿主支持矩阵有据可查：写明哪些宿主用官方 NDK、哪些用仓库内脚本，附核实日期与来源
- [ ] 一条通路：所有宿主都用同一组步骤生成四个原生库（渲染器、会话层、bootstrap、local-socket）并放进打包输入目录；不再依赖 AGP 的 externalNativeBuild 产物
- [ ] 应用模块与会话层依赖模块的原生构建配置与"一条通路"一致，不再保留会走假 NDK 的 ndkBuild 声明
- [ ] 原生库生成脚本自检输入：先校验 bootstrap 归档的 sha256，缺失或哈希不符就明确失败并给出获取指引
- [ ] 产物 ABI 范围收窄到项目目标设备实际支持的范围，不再产出没有原生库的空 APK 变体
- [ ] 构建校验脚本断言四个原生库齐全，缺任一个就非零退出
- [ ] 反向测试：故意去掉一个原生库后，构建校验脚本必须失败；证据写进 Comments
- [ ] fresh clone 上按 README 从零走一遍即可产出 APK：包名 `com.gph.fable`、显示名与签名符合文档、`lib/` 下四个库齐全
- [ ] 真机安装验证：App 能启动，bootstrap 安装与终端启动正常
- [ ] 三个 Rust crate 的质量门禁与供应链门禁通过；秘密扫描 0 命中；构建输入 sha256 与来源表一致
- [ ] 文档同步：README、构建输入来源表、项目总览与交接 三处写明 NDK 版本、宿主矩阵、aarch64 宿主的做法
- [ ] 交付一份 ADR：构建链宿主矩阵与单一原生库通路（记录"官方没有 Linux aarch64 NDK"这一事实与核实日期）
- [ ] 不违反 ADR-0012：预编译 `.so`、bootstrap 归档、Apple 字体都不进版本库；应用身份不改

## Comments

2026-10-02 建单。来源是工单 65 的失败项：fresh clone 按 README 构建出的 APK 缺 `libtermux-bootstrap.so` 与 `liblocal-socket.so`。根因是设备上的 `ndk;22.1.7171670` 是手写替身，它忽略 AGP 9 建立构建模型用的 `-n`，AGP 得到的库列表为空，ndkBuild 产物进不了 merge；工作区靠 2026-08-06 留下的两个旧库掩盖了这个问题。

2026-10-02 核实：官方 SDK 仓库（`dl.google.com/android/repository/repository2-3.xml`）里没有 Linux aarch64 的任何包。按 `<host-arch>` 统计：linux 只有 x64；aarch64 只有 macosx。所以"在手机上装官方 aarch64 NDK"不可行，本单按"宿主矩阵 + 仓库内脚本"设计。

宿主矩阵（待写进文档）：

| 宿主 | 官方 NDK | 本项目的做法 |
| --- | --- | --- |
| Linux x86_64 / Windows x64 | 有 | 官方 NDK，走仓库内脚本调用它的 clang |
| macOS x64 / macOS arm64 | 有 | 同上 |
| Linux aarch64（Termux 手机、aarch64 Linux 电脑） | 无 | Termux clang + ndk-sysroot，同一个脚本换编译器 |

工单 65 的推送部分等本单完成后重跑。
