## 背景

- 代码库现状：termux-app fork，**纯 Java**；UI 目前全部 XML + 经典 View（TermuxActivity 等）；TerminalView 是自绘渲染视图，会话层底盘已定（工单 01/07 后 Fable 可运行）。
- 构建链：aarch64 手机本地构建 + JDK 17 + Gradle 7.2 + 假 NDK/aapt2 覆盖；构建约束多（详见交接文档与 13 坑记录）。
- 交接文档对 UI 框架"倾向 Compose"，但**那只是倾向，不是决策**——必须以代码库事实重新评估。

## 工单任务（只做决策与文档，不改代码）

1. **UI 框架选型定案**：Compose（需引入 Kotlin 工具链）vs 继续 XML/经典 View。至少从以下维度给出带证据的评估：
   - 与纯 Java 代码库的兼容性/迁移成本（Compose 对 Java 的支持现状）
   - TerminalView 嵌入方式（AndroidView vs 直接布局）
   - 构建链可行性：Gradle 7.2 + JDK 17 + aarch64 本地构建能否稳定引入 Kotlin/Compose（重点验证依赖下载与编译耗时）
   - 重写范围与风险、长期维护成本
   给出明确结论（可以推翻"倾向 Compose"，只要证据成立）。
2. **产出 v1 最小集清单**：字号、主题、键盘布局、会话恢复等"什么算做完"，逐项写**可验收标准**（用户能逐项勾选）；范围与 spec 用户故事 8/15 一致，不得蔓延。
3. **写 ADR**：选型结论记录到 `docs/adr/`（若为空从 `0001` 起编号），包含结论、理由、被否选项与原因。
4. **呈现给用户确认**：本工单验收含"经用户确认"——把选型结论 + 最小集清单交给用户拍板（可以一次问清，不要分多次打断）。确认后把结果写回工单 03 `## Comments`，更新 `Status:`。
